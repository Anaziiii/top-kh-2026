**Мета роботи** - познайомитися з найбільш поширеними сучасними принципами проєктування програмного забезпечення.

## Хід роботи 

1. Опрацьовано загальні принципи, яких дотримуються під час написання коду:
    - **KISS** - код має бути якомога простішим, без зайвих ускладнень;
    - **DRY** - однакова логіка не повинна повторюватись у кількох місцях;
    - **YAGNI** - не варто писати функціонал "на майбутнє", поки він не потрібен.
2. Розглянуто набір принципів **SOLID** для об'єктно-орієнтованих програм:

    | Принцип | Назва | Що означає |
    |---------|-------|------------|
    | **S** | Single Responsibility | у класу одна зона відповідальності |
    | **O** | Open/Closed | клас відкритий для розширення, але закритий для змін |
    | **L** | Liskov Substitution | нащадок може замінити базовий клас без поломок |
    | **I** | Interface Segregation | краще кілька малих інтерфейсів, ніж один великий |
    | **D** | Dependency Inversion | залежати потрібно від абстракцій, а не від конкретних класів |

3. Для практичної частини [lab11](lab11.py) вибрано принцип **відкритості/закритості (OCP)**. За основу взято клас **Dog** з попередніх лабораторних.
4. Створено абстрактний клас **FeedingPlan** з методом **daily_portion**, який рахує денну норму корму. Від нього успадковано три раціони: **PuppyPlan**, **AdultPlan** і **SeniorPlan**, кожен зі своєю формулою.
5. Клас **Kennel** (розплідник) зберігає собак разом з їхніми раціонами і виводить меню на день. У ньому немає жодної перевірки типу раціону через **if**, він просто викликає **daily_portion**.
6. Завдяки цьому, щоб додати новий раціон (наприклад, для собак на дієті), достатньо написати ще один клас-нащадок **FeedingPlan**. Код класу **Kennel** та існуючих раціонів змінювати не потрібно.

## Висновок
У підсумку виконання лабораторної роботи ознайомився з принципами KISS, DRY, YAGNI та п'ятьма принципами SOLID. На практиці застосовано принцип відкритості/закритості на прикладі розрахунку раціону для собак у розпліднику.

Переконався, що коли поведінка винесена в окремі класи зі спільним інтерфейсом, програму можна розширювати без втручання у вже написаний і перевірений код, а отже менший ризик щось зламати.
